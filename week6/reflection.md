# Stage 3 – Reflection

The hardest modeling decision was about where to put has_clash(). An Appointment object only knows its own time and practitioner, and so can't see the other bookings it might clash with. I decided to keep an AppointmentManager class that contains all appointments and performs the clash check across them.
Copilot over-designed by suggesting a Receptionist class, but it had no attributes, and its operations only described what the receptionist does as a user of the system, so it added a class without adding meaning. The tutorial's AI also suggested separate Manager, Controller and Engine classes. I only kept AppointmentManager because the clash check needs it; the others split one simple responsibility across several classes without meeting any extra requirement. In one place Copilot was too strict instead: it said Practitioner should have no attributes at all, but FR-12 needs practitioner names to be listed, so I kept the ID and name and marked them as assumptions.
My final choices were based on the requirements. For example, keeping has_clash() in AppointmentManager (FR-03), using an enum for appointment status instead of free-text strings (FR-04), and keeping practitioner names as attributes (FR-12).
